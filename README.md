# Prayog (प्रयोग, "experiment")

Small-scale, controlled reproductions of key claims from well-known LLM fine-tuning, RL and systems papers.
Each experiment uses fixed seeds, several runs, reports mean ± std over seeds, and states plainly whether the
paper's claim **reproduced**, **partly reproduced**, or **did not reproduce**. Everything here runs on a laptop CPU;
GPU work lives separately in [`gpu/`](gpu/README.md) and is labelled by what has actually been run.

**Rule of the repo:** every number below comes from a saved `experiments/<name>/results.json`. The tables are
generated by `python scripts/build_cards.py`, which also produces each experiment's repro card
(`experiments/<name>/card.json`, shown in the dashboard). Verdicts are computed by a rule in that script.

### LoRA vs full fine-tuning: **partly reproduced**

_Hu et al. 2021, LoRA: Low-Rank Adaptation of Large Language Models_

Full FT accuracy 0.767 ± 0.017 with 100% trainable parameters. lora_r1 0.726 ± 0.015 (0.03% trainable); lora_r4 0.733 ± 0.027 (0.10% trainable); lora_r16 0.728 ± 0.020 (0.38% trainable). Best LoRA (lora_r4) is 3.3 accuracy points below full FT (seed std up to 2.7 points). Training took 61s (full) vs 37s (LoRA r=4), 1.6x faster; analytic training-state memory 66.9 MB vs 16.8 MB.

| variant | val accuracy | trainable % | train time (s) | state memory (MB) |
|---|---|---|---|---|
| full_ft | 0.767 ± 0.017 | 100.000 ± 0.000 | 60.6 ± 1.6 | 66.9 ± 0.0 |
| lora_r1 | 0.726 ± 0.015 | 0.029 ± 0.000 | 38.8 ± 2.3 | 16.8 ± 0.0 |
| lora_r4 | 0.733 ± 0.027 | 0.099 ± 0.000 | 37.4 ± 2.6 | 16.8 ± 0.0 |
| lora_r16 | 0.728 ± 0.020 | 0.378 ± 0.000 | 38.9 ± 1.9 | 17.0 ± 0.0 |

What did not match the paper:
- The paper reports parity with full FT on large models; here a gap remains on a 4.4M-parameter model.
- Accuracy does not increase with rank (r=1, 4, 16 are within noise of each other), which agrees with the paper's 'low rank suffices' point but means we cannot show a rank trend.
- Memory is an analytic estimate (weights + gradients + Adam states), not measured peak memory; activations are excluded.
- Learning rates were set once, not swept; the LoRA/full gap may shrink with tuning.

### Knowledge distillation: **partly reproduced**

_Hinton, Vinyals, Dean 2015, Distilling the Knowledge in a Neural Network_

Student alone 68.97 ± 0.39% vs distilled: T=1 70.00 ± 0.84%; T=2 69.01 ± 2.38%; T=4 69.01 ± 2.66%; T=8 70.83 ± 1.35%. Best is distilled_T8 (+1.86 points over student alone; seed std up to 1.35).

| variant | val accuracy |
|---|---|
| student_alone | 0.6897 ± 0.0039 |
| distilled_T1 | 0.7000 ± 0.0084 |
| distilled_T2 | 0.6901 ± 0.0238 |
| distilled_T4 | 0.6901 ± 0.0266 |
| distilled_T8 | 0.7083 ± 0.0135 |

What did not match the paper:
- The gains are small and mostly within seed noise; the paper reports clear gains on larger problems.
- The student stays far below the teacher; bert-tiny with 1000 labelled examples is capacity/data limited.
- The teacher was trained on the full SST-2 train set, which includes our 1000-sentence subset.
- We did not use a separate unlabelled transfer set, so distillation sees no extra inputs.

### Preference optimisation (DPO) and AI-judge labels: **partly reproduced**

_Rafailov et al. 2023, Direct Preference Optimization; Bai et al. 2022 (RLAIF)_

Held-out pairs where the model ranks the human-chosen reply higher (length-normalised log-likelihood): untrained 49.0%, DPO on human labels 54.7 ± 0.8%, DPO on judge labels 56.2 ± 1.8%. DPO implicit-reward accuracy: human 59.2 ± 2.5%, judge 55.8 ± 3.8%. Rule-based quality pass rate: untrained 10%, human 15%, judge 12%. The judge agrees with human labels on 58.3% of 600 pairs (chance = 50%); the agreement figure uses the order-debiased score (A-B logit gap averaged over both answer orders); the judge picked the same underlying reply in both orders for only 0% of pairs (0 of 600), i.e. it is dominated by position bias.

| variant | held-out pref acc (logp) | held-out pref acc (DPO reward) | rule pass rate |
|---|---|---|---|
| untrained | 0.490 ± 0.000 | 0.000 ± 0.000 | 0.10 ± 0.00 |
| dpo_human_labels | 0.547 ± 0.008 | 0.592 ± 0.025 | 0.15 ± 0.08 |
| dpo_judge_labels | 0.562 ± 0.018 | 0.558 ± 0.038 | 0.12 ± 0.01 |

What did not match the paper:
- pythia-70m is a base model, not instruction-tuned, so 'better responses' cannot be judged by humans or meaningfully by a rule; the rule check only catches degenerate or role-leaking output.
- The 0.5B local judge is weak; its agreement with humans should be read against the 50% chance level.
- Preference accuracy on held-out pairs is a proxy; we did not run a win-rate evaluation.
- The untrained model's implicit-reward accuracy is 0 by construction (policy equals reference).
- IBM watsonx.ai Granite judge adapter exists in prayog/judge.py but was not run.

### PPO: library vs from-scratch: **reproduced**

_Schulman et al. 2017, Proximal Policy Optimization Algorithms_

SB3 PPO final return 500.0 ± 0.0; scratch PPO 495.6 ± 9.8 (max 500). Difference 4.4. Training took 81s vs 74s per run.

| variant | final eval return | train time (s) |
|---|---|---|
| sb3_ppo | 500.0 ± 0.0 | 81 ± 2 |
| scratch_ppo | 495.6 ± 9.8 | 74 ± 1 |

What did not match the paper:
- CartPole saturates at 500, so the final score cannot separate two good implementations; the learning curves (below) are the better comparison.
- LunarLander was not run (Box2D is not installed on the development machine), so only CartPole is covered.
- The paper's experiments are on MuJoCo/Atari; CartPole is a much easier problem.
- Greedy evaluation is used for the final score; training curves use stochastic-policy episode returns.

## Run it

```bash
python -m venv .venv && . .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python experiments/lora_vs_full/run.py              # add --smoke for a tiny CPU check
python experiments/distillation/run.py
python experiments/rl_ppo/run.py
python experiments/dpo/run.py                       # slow: downloads a 0.5B judge, judges 600 pairs
python scripts/build_cards.py                       # results.json -> card.json + README tables
uvicorn app.main:app --app-dir backend --port 8000  # API
cd frontend && npm ci && npm run dev                # dashboard on :5173 (proxies /api)
```

Docker: `docker compose up --build` serves the dashboard and API on http://localhost:8000 (MLflow UI on :5000).
Runs are also logged to MLflow (file store in `./mlruns`).

## PPO, GAE and the clipped objective, in my own words

Policy gradient asks: make actions that turned out better than expected more likely. "Better than expected" is the
**advantage**, `A_t = (what actually happened from t) − (what the value network predicted for s_t)`.
Using the full return gives an unbiased but very noisy advantage; using only a one-step estimate
`δ_t = r_t + γV(s_{t+1}) − V(s_t)` is low-noise but biased if `V` is wrong.
**GAE** blends the two: `A_t = δ_t + γλ δ_{t+1} + (γλ)² δ_{t+2} + …`, computed backwards in one pass.
`λ = 0` is the one-step estimate, `λ = 1` is the full return minus the baseline; 0.95 is a common middle.
Episode ends cut the sum so nothing leaks across episodes (`compute_gae` in `experiments/rl_ppo/ppo_scratch.py`).

Plain policy gradient can take one bad, huge step and wreck the policy. PPO reuses each batch for several epochs, so it
needs to stop the policy drifting from the one that collected the data. With `r = π_new(a|s) / π_old(a|s)`, the
**clipped objective** is `min(r·A, clip(r, 1−ε, 1+ε)·A)`. If an action was good (`A>0`), pushing its probability up
stops being rewarded once `r > 1+ε`; if it was bad, pushing it down stops being rewarded once `r < 1−ε`. The `min`
keeps the pessimistic of the two, so there is no gain from moving the policy far from where the data came from,
without needing a hard KL constraint.

## Honest limits

- Tiny models and small data (bert-tiny, pythia-70m, CartPole). These runs test whether a claim *shows up* at small
  scale, not whether the paper's headline numbers hold.
- The weights of the AI judge (Qwen2.5-0.5B-Instruct) are small; its labels are noisy. watsonx.ai Granite judge: adapter
  written in `prayog/judge.py`, **not run** (no key).
- LunarLander and the GRPO-style experiment were **not run**.
- GPU parts (Triton kernels, NCCL/DDP) are **not run**; there is no GPU on the dev machine and no GPU numbers are claimed.
- Live deployment is not part of this repo's history; see "Deploy".
